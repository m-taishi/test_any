ODM Pipeline Analysis / Databricks

2万件のパイプラインを
データ需要の行動ログとして読み解く

ODMに存在する約20,000件のデータパイプライン（XML）を解析し、銀行内で繰り返し発生してきたデータ需要と加工パターンを構造として復元する。
目的は「2万本を移植すること」ではなく、複数部門・複数用途から再利用できる共通データ資産の候補を、コードの利用実態から発見することである。

Why

2万件のパイプラインは、移行対象ではなく需要の記録である

同じ資産を「何を移すか」で見るか「何が求められてきたか」で見るかで、得られる結論が変わる。

従来の見方：移行対象の山
パイプライン1本ずつを個別資産として数え、移植可否・工数・依存関係を積み上げる。

結果として得られるのは「2万本の作業リスト」であり、重複した加工や重複した中間データはそのまま新環境へ持ち込まれる。
重複が温存される
今回の見方：データ需要の行動ログ
1本のパイプラインを「誰が・どのデータを組み合わせ・どう加工し・何を作ろうとしたか」の記録として読む。

2万本を横断して集計すれば、繰り返し発生している共通のデータ需要が統計的に浮かび上がる。
共通資産として集約できる
個別ユーザー・個別部門で重複して作られている中間データと加工ロジックを発見し、複数ユースケースから再利用可能な汎用データマート候補を抽出する。
Definition

「汎用データマート」をどう定義するか

複数の既存データパイプラインで共通して利用・生成されているデータ、加工ロジック、業務定義を標準化し、
特定の帳票・分析・ユーザーに依存せず、複数の分析・AI・業務ユースケースから再利用可能にしたデータセット。
依存しない
特定の帳票、特定の分析、特定の作成者に紐づかない。用途が消えても価値が残る単位で切る。
再利用される
複数部門・複数Output・複数年にわたって参照される。単発需要と恒常需要を明確に分ける。
標準化されている
データ構造だけでなく、JOINキー・粒度・集計定義まで揃っていて初めて共通資産になる。
重要：「よく使われる既存テーブル」をそのまま汎用化することではない
今回重視するのは、InputからOutputへ至る途中で、複数Pipelineが繰り返し同じテーブル群をJOIN・加工して作っている「共通中間層」を見つけることである。

As-Is

現状：同じ中間データが Pipeline ごとに作り直されている

複数の部門が、それぞれのOutputのために、毎回ゼロから同じテーブル群をJOINしている。

同じ CUSTOMER + ACCOUNT + TRANSACTION の結合結果が、Pipelineごとに別々に生成・保持されている。加工の重複、定義のばらつき、計算コストの重複が同時に発生する。
To-Be

目指す姿：共通中間層を一度だけ作り、後続から再利用する

複数Pipelineに共通する連結部分を切り出す。その共通中間層そのものが汎用データマート候補になる。

最大の問いは 「どこまでを共通中間層として作り、どこから先を個別Pipelineに任せるか」。この境界を、コードの利用実態から定量的に導く。
Approach

全体アプローチ：構造化 → グラフ化 → 連結分析 → 意味付け

最初から全件に詳細解析やLLM解析をかけない。安価で決定論的な処理で範囲を絞り、最後だけ解釈を足す。

Core Idea

単一テーブルの頻度だけでは、何を作るべきかが決まらない

分かること
Fan-out / Fan-in を見れば頻出テーブルは分かる。
CUSTOMER が 1,500 Pipeline で使われる
しかし CUSTOMER は既にある。これは作るべき新しい資産の姿を教えてくれない。
本当に知りたいこと
複数Pipelineで繰り返しセット利用されるテーブル群。
CUSTOMER + ACCOUNT
CUSTOMER + ACCOUNT + TRANSACTION
CUSTOMER + ACCOUNT + TRANSACTION + PRODUCT
これを本資料では Connected Table Set と呼ぶ。
なぜ「セット」が重要か
個々のテーブルは既に存在しているため、汎用化の対象はそれらを結合した結果である。
繰り返し同じ組み合わせが結合されているということは、その結合結果自体に恒常的な需要があることの証拠になる。
Definition

第N連結 ＝ N本のJOIN Edgeで連結される N+1 種類のテーブル集合

分析対象は単なるPATHではなく、同一Pipeline内でJOINにより接続された Connected Table Set である。

① 一直線のJOIN
② 一直線でない構造も対象
正規化ルール（必須）
テーブル集合の並び順で別候補にならないよう、array_sort(table_set) → concat_ws('||', ...) で table_set_key を生成する。
CUSTOMER||ACCOUNT||TRANSACTION と TRANSACTION||CUSTOMER||ACCOUNT は必ず同一候補として扱う。JOIN Edge も table_pair_key をソートして生成する。

  • 20,000 × 20,000 の Cross Join は禁止

Metric

維持率（Retention）で 汎用化境界 を定量的に捉える

retention_rate
child_pipeline_count
/ parent_pipeline_count
親子1組ごとの維持率。720 / 850 = 84.7%
parent_support_retention
child_pipeline_count
/ MAX(parent_pipeline_count)
Parent候補が複数ある場合、最もPipeline数が多いParentを基準にした維持率。
max_child_retention
MAX(すべての子の
retention_rate)
これが低いほど、その集合から先は個別化が進んでいる＝境界の可能性が高い。
Parent / Child の定義
Childのtable setから1テーブル除いた集合がParentに存在すれば親子候補。
Parent [A,B,C] → Child [A,B,C,D] なら added_table = D。
[A,B,C] には [A,B] [A,C] [B,C] という複数Parentがあり得るため、すべての親子関係を保存する。
汎用化境界候補の特徴
  • 自身の Pipeline利用数が多い
  • 複数部門から利用されている
  • 複数Outputに利用されている
  • ここまでは高い共通性を維持している
  • さらにテーブルを足すと利用Pipeline数が急減する
暫定の候補判定ルール（パラメータ化して後から変更可能にする）： pipeline_count >= 5 AND department_count >= 2 AND max_child_retention < 0.5 → candidate_flag = true。この閾値は業務的な正解ではない。判定から漏れたデータも削除せず保持する。

Fingerprint

Pipeline Fingerprint：名前ではなく処理構造で比較する

Pipelineが「何を入力し、どのように加工し、どの粒度で出力するか」という処理の特徴を、比較可能な形式で表したもの。
正規化してHash化する
INPUT=CUSTOMER,DEPOSIT,INVESTMENT
|JOIN=customer_id
|AGG=SUM(balance)
|GROUPBY=customer_id,year_month
表記順・大文字小文字・空白・alias差・関数名表記を正規化した上で SHA-256 でHash化する。
P001 → 8AF3897C...
P032 → 8AF3897C...
P182 → 8AF3897C...
同じHash＝実質的に同一の処理をしている可能性が高い。
A. Exact Fingerprint
literal値・条件値も含めて完全一致を見る。実質的に同一ロジックの検出用。
B. Structural Fingerprint
日付・数値・文字列などの literal を <LITERAL> にパラメータ化する。条件値だけ違うテンプレート処理の検出用。
ただし カラム名・JOINキー・集約関数・GROUP BY粒度など業務ロジックに影響する情報は保持する。
近似類似の扱い
20,000 × 20,000 の直積は禁止。input table数・共通input・output数・structural hash prefix 等でbucketしてから Jaccard 類似度を計算する。大規模化する場合は MinHashLSH を検討する。
Interpretation

Fingerprint → Cluster → Semantic：LLMは最後の解釈だけ

Fingerprintの完全一致だけでは、少し処理が異なる類似Pipelineを捉えられない。段階的に束ねてから意味を与える。

P001: CUSTOMER + DEPOSIT + INVESTMENT → SUM(balance)
P002: CUSTOMER + DEPOSIT + INVESTMENT + TRUST → SUM(balance)
Hashは異なるが、業務的にはどちらも「顧客金融資産」を作っている可能性がある。

Guardrails

非交渉の実装ルール（ガードレール）

再現性・監査性・安全性を守るための前提。実装者・AIエージェントのどちらに対しても同じ制約をかける。

既存資産を壊さない
既存テーブルへの DROP / TRUNCATE / DELETE / 破壊的 OVERWRITE は禁止。書き込みは専用の TARGET_CATALOG.TARGET_SCHEMA に限定する。同名テーブルがある場合はスキーマと行数を確認してから MERGE する。
推測で補完しない
XMLに存在しない業務定義・部門・テーブルの意味を推測しない。不明値は NULL または UNKNOWN として保持する。pipeline_id が欠落しても業務IDを生成せず TECH:<file_hash> とする。
仕様不明のまま全量Parseしない
必ずサンプル観察とマッピング確定を先に行う。XML構造が複数パターンある場合は parser_version / xml_pattern を記録し、パターン別に処理する。
計算量を爆発させない
Pipeline間の 20,000 × 20,000 直積を作らない。まず Hash / Bucket / 入力集合で候補を絞る。連結生成は Pipeline 内で完結させ、各Depthで重複排除する。
LLMは最小限・後段のみ
構文・構造解析は Spark / Python で決定論的に行う。20,000件全件を LLM へ送らない。Raw XML本文や業務データを外部へ送らない。APIキー・Secretをノートブックへ平文で書かない。
冪等性と検証を必須にする
同一ファイルを再実行しても重複行が増えないよう file_path + file_hash や pipeline_id をキーにする。各フェーズ終了時に検証SQLを実行し、行数・NULL率・重複・エラー件数を表示する。エラーは握りつぶさず原因と修正内容を残す。

Summary

まとめ：6つの視点と、超えてはいけない一線

Graph
どこで・どれだけ使われているか
Connected Table Set
どのテーブル群がセットで使われているか
第N連結 / Retention
どこまでを共通中間層にすべきか
Fingerprint
そのテーブル群をどのように加工しているか
Cluster
どのPipeline同士が似ているか
Semantic
業務的に何を作ろうとしているか
よくセットでJOINされる ＋ 複数Pipelineで使われる ＋ 複数部門で使われる ＋ 複数Outputに再利用される ＋ 第N連結まで共通性が維持される ＋ それ以上の連結で個別化が進む ＋ 加工ロジックも共通・類似している
— そのような中間データほど、個別Pipeline内で毎回作るのではなく、共通データ資産として一度整備し再利用する価値が高い。
注意事項：コード上の頻出は、業務定義として正しいことを意味しない
Connected Table Set が頻出していても、JOINキー・JOIN Type・Filter条件・粒度・対象商品/顧客範囲が異なる可能性がある。
コード分析 → Connected Table Setの発見 → 汎用化境界候補の抽出 → Fingerprintによるロジック確認 → 業務定義の確認・統一 → 正式な汎用データマート
コード解析結果は「共通データ需要を発見するための証拠」であり、そのまま正解データ定義としないことが重要である。
